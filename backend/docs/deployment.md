# Deploying the Solar Care API

## Configuration and startup

Use [the environment template](../.env.example) to provision separate development, staging and production environments. Staging enforces the same checks as production. Keep deployed secrets in the platform secret manager. Use independent cryptographically generated customer JWT, admin JWT and rate-limit secrets for each environment. Provide the runtime PostgreSQL URL, exact trusted hostnames and HTTPS CORS origins through process environment variables. Backend .env files are for local development.

Install requirements.txt under Python 3.12 from the backend directory and start with `python -m app.serve`. Set `APP_ENVIRONMENT` to staging or production in the launcher process. Container hosts can build the included Dockerfile with backend as the context. Set `PORT` to the platform listener port, `WEB_WORKERS` to the worker count, `WEB_CONCURRENCY` to the per-worker concurrency cap and `GRACEFUL_SHUTDOWN_SECONDS` within the host's termination window. Start with one worker. Each worker can have four active Argon2id computations at 64 MiB each. Account for CPU, RAM and database capacity across workers and replicas.

Terminate TLS at ingress, redirect HTTP there and enable HSTS once HTTPS is verified on the intended domains. Restrict backend access to the ingress or private network, preserve the public Host, overwrite untrusted forwarding headers and configure `TRUSTED_PROXY_IPS` with the actual proxy IPs or dedicated CIDRs. An empty list disables forwarded header processing. Set ingress request and header size limits and timeouts. The API also rejects oversized bodies with HTTP 413. Include the host used by platform probes in `TRUSTED_HOSTS`. [Uvicorn server settings](https://www.uvicorn.org/settings/)

List exact HTTPS browser origins in `ALLOWED_CORS_ORIGINS`. If browser admin refresh cookies are used, also list those origins in `ADMIN_BROWSER_ORIGINS`. Use same-site HTTPS origins with the Secure, HttpOnly and SameSite=Strict cookie. The admin access token uses the authorization header. Native React Native clients use bearer authentication independently of browser CORS.

Customer and admin tokens use separate signing keys, issuers and audiences. Access tokens are short-lived. Refresh tokens are hashed, rotated and checked against session and account state. Plan for client reauthentication during signing-key rotation and review outstanding refresh sessions separately.

## PostgreSQL and release jobs

Use a dedicated least-privilege runtime role. Use TLS and prefer sslmode=verify-full with a trusted CA mounted as a secret. Direct and session mode use pre-ping and recycling and cap connections at `DB_POOL_SIZE + DB_MAX_OVERFLOW` per worker. Multiply by workers and replicas and reserve capacity for release jobs and operators. Transaction mode uses the external pool without a second application pool and disables automatic prepared statements. Limit concurrency within the pooler's client budget. Set and verify runtime-role statement and idle-in-transaction timeouts through the selected connection mode. Keep browser-facing Supabase roles outside private tables. Because the migrations enable RLS, a non-owner runtime role needs explicit policies scoped to that backend-only role as well as grants. Verify its access before cutting traffic. Do not grant these policies to anon or authenticated. [Supabase connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres)

1. Confirm a verified restore point. Test the migration and application on staging with representative data. Use `alembic upgrade head --sql` or an explicit offline revision range to review the SQL.
2. Run one release job from backend in the new checkout or image. Supply `MIGRATION_DATABASE_URL` for the schema role, using a direct or session-pooled connection. It is required for migration runs when the runtime uses the transaction pooler. Run `alembic current`, then `alembic upgrade head`, then verify the new revision. Web workers never apply migrations.
3. Phase 9 adds a nullable audit request ID and a technician workload index. It caps lock acquisition at five seconds. Schedule a quiet window for a large assignment table because the index build can block writes.
4. Revision `20261112_0009` supports pending bookings with no date or address. It publishes Solar Panel Cleaning with pricing to be confirmed if the catalogue has no records. Existing services, including inactive ones, are preserved. Deploy the updated API and dashboard before distributing the updated mobile app. Smoke-test `/api/v1/services` and an optional-details booking with a test account.
5. On failure, stop the release, check the revision and transaction result, resolve the cause and retry the reviewed job. Keep the previous app image available. Use a forward corrective migration to preserve data. If restore is required, recover to an isolated target first and reconcile writes after the restore point.
6. Deploy the web workers after migration succeeds. Check readiness and liveness and test a booking read and an audited operation with designated accounts.

## Operations and privacy

- Use `GET /health` for process liveness and `GET /health/ready` for traffic readiness. Readiness runs a lightweight database query and returns HTTP 503 on connection failure. Versioned aliases are under `/api/v1` by default.
- Sensitive routes use configurable limits by source and operation. PostgreSQL atomically updates HMAC-keyed buckets shared across workers. Admin login keeps its source, source/account and account limits under `ADMIN_LOGIN_*`. HTTP 429 includes Retry-After in seconds. Shared NAT clients share a source bucket and IPv6 sources are grouped by /64. Keep worker clocks synchronized. Set `RATE_LIMIT_SECRET` to exercise shared limits in development. [PostgreSQL atomic conflict updates](https://www.postgresql.org/docs/current/sql-insert.html)
- Include periodic removal of expired abuse counters from admin_login_buckets in database maintenance. Use the existing window_started_at index, small batches, and a cutoff safely beyond the maximum configured window, such as seven days. Retain audit and booking records according to the approved retention policy.
- JSON logs include timestamps, generated request IDs, route templates, methods, statuses and timing. API audit records carry the same ID. Restrict log access and configure ingress logging to omit authorization headers, cookies, query strings and request bodies.
- Restrict customer addresses and phone numbers through the existing ownership and admin permission rules. Keep internal notes private and limit any future technician API to information required for current assignments. Account deactivation revokes sessions while preserving booking history.
- The public browser pages are `/`, `/privacy-policy` and `/contact-us`. JSON is available at `GET /api/v1/privacy-policy` and `GET /api/v1/contact-us`. Publish the active business profile with a support email or phone. Set `PUBLIC_PRIVACY_EFFECTIVE_DATE` after the business approves the wording and confirms its retention and handling practices.
- The private object storage contract lives in app/core/storage.py. Before adding uploads, authorize access to the booking and its media, decode and validate file contents and dimensions, strip metadata and issue short-lived signed URLs only after a separate access check.
- Keep booking and assignment writes in their database transactions. Future reports, reminders and notifications can call existing services from a separate runner. Use idempotent jobs and a durable outbox for notifications that must follow a committed transaction.

## Backup and recovery

Set recovery-point and recovery-time targets with the business. Confirm the database plan's backup cadence, retention and point-in-time recovery options. Configure automated encrypted backups and an independent copy where required. Restrict access and retain copies for the approved period. Verify backups by restoring to an isolated database and checking the migration revision, permissions, essential record counts and representative app flows. [Supabase backup and recovery](https://supabase.com/docs/guides/platform/backups)

During an incident, preserve the affected database and logs, identify a known-good point, restore to an isolated target, validate data and permissions and reconcile transactions after that point before switching traffic. Record the outcome and repeat backup verification on a schedule. Track future object-storage backups separately.
